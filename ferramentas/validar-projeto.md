# Validar um projeto contra o kit

O prompt para conferir se um repositório segue o kit Trilha AI. Cole-o como está numa sessão do
Claude Code: ele pergunta primeiro o nome da pasta do projeto, que fica sempre em
`/home/pl/projetos/<nome>`. Ele só audita: grava o relatório em
`<pasta>/docs/validacao-trilha-ai.md` e não corrige nada.

```text
Antes de qualquer outra coisa, pergunte o nome da pasta do projeto a validar e espere a resposta. É só o nome (por exemplo, xavier): todo projeto fica em /home/pl/projetos/<nome>, e é esse caminho que <pasta> quer dizer daqui em diante. Se a pasta não existir ou não for um repositório git, diga isso e pergunte de novo.

Valide o repositório <pasta> contra o kit Trilha AI que está em /home/pl/projetos/trilha-ai. É uma auditoria: não corrija nada, não commite e não mexa no ANDAMENTO.md. O único arquivo que você grava é o relatório.

A pasta do método é a trilha-ai/ desde a 2.19. Num projeto da 2.0 à 2.18, ela é a trilha/ (a que tem o trilha/CLAUDE-comum.md): nos itens 1 a 5, use trilha/ no lugar de trilha-ai/ (os verificadores, o core.hooksPath em trilha/hooks e a trava em trilha/guarda.py) e recomende o python3 ferramentas/kit.py atualizar <pasta>, que leva o projeto à trilha-ai/. Desde a 2.20, a trilha que é um link simbólico para a trilha-ai/ (readlink trilha dá trilha-ai) é o link de transição, e não uma migração pela metade: por ele, o que o projeto ainda chama pela pasta antiga continua funcionando. É aviso no item 1, e a pendência é trocar as citações a trilha/ que o kit.py atualizar lista; o próximo kit.py atualizar sem citação tira o link. Se o projeto tiver as duas com o CLAUDE-comum.md sem ser esse link (test -f trilha/CLAUDE-comum.md, a evidência no item 1), é uma migração pela metade: a versão e os itens 1 a 5 são os da trilha-ai/, e a trilha/ que sobrou é falha no item 1, que nenhum verificador aponta. A correção é o mesmo kit.py atualizar, que a tira, mas ele recusa sem mudar nada quando a trilha/ é um link simbólico (test -L trilha) ou tem arquivos que o git ignora (git ls-files -o -i --exclude-standard -- trilha/, fora do __pycache__): diga qual dos dois e que eles saem de lá antes, por escolha do usuário. Num projeto noutra versão que a do kit, os itens 5, 6 e 9 comparam com o modelo da tag vX.Y do projeto (git -C /home/pl/projetos/trilha-ai show vX.Y:modelo/<arquivo>), e o que só a versão nova do kit muda vai à recomendação do kit.py atualizar, não às falhas.

Confira, rodando os comandos e lendo o código de saída de cada um:
1. A cópia do kit: a pasta do método existe; anote a versão do CLAUDE-comum.md do projeto e a do kit. Desde a 2.4, a comparação dela com a do kit é a do item 2 (o --fonte): na mesma versão, com a cópia de trabalho do kit; noutra, com a tag vX.Y, que ele lê pelo git sem extrair nada. Da 2.0 à 2.3, o --fonte compara com a cópia de trabalho do kit, que é de outra versão: as linhas da pasta do método no item 2 ("trilha/… falta", "não é do kit", "difere do kit", "perdeu a permissão") não contam; compare-a com a da tag (git -C /home/pl/projetos/trilha-ai archive vX.Y modelo/trilha | tar -x -C <pasta temporária vazia>, e diff -r, ignorando __pycache__).
2. As regras: python3 -I trilha-ai/confere_regras.py . --fonte /home/pl/projetos/trilha-ai
3. O método: python3 -I trilha-ai/confere_metodo.py, com os --vizinho que o scripts/check.sh do projeto usa.
4. A verificação completa: bash scripts/check.sh, sozinho, sem filtro.
5. As travas: git config core.hooksPath (deve ser trilha-ai/hooks; trilha/hooks com o link de transição é aviso para trocar, não falha); o .claude/settings.json comparado ao modelo/claude-settings.json: o guarda.py e, desde a 2.2, o plugin sdd@trilha-ai.
6. Os documentos: o PRD, o TDD e a decomposição em sdd/; o ANDAMENTO.md; o openspec/config.yaml comparado ao modelo/openspec/config.yaml do kit. O context é do projeto. De rules: até o fim, o texto é o do kit: só passam linhas próprias a mais no operations e chaves de topo do próprio OpenSpec (o githubCopilot). Qualquer outra diferença nas regras é desvio, mesmo com um ADR que as chame de próprias, salvo exceção declarada em "Exceções ao comum" do CLAUDE.md, com o motivo. Desde a 2.7, o item 2 reprova o rules: diferente.
7. O CI: o .github/workflows roda o scripts/check.sh.
8. Os dados: arquivos no git com dados pessoais ou segredos, fora do que o "Dados a proteger" do CLAUDE.md permite.
9. As ferramentas da máquina: o openspec --version diante do @fission-ai/openspec@X do CI do projeto; o perfil do OpenSpec (openspec config list), com o verify e a entrega em skills e comandos (both); os avisos do OpenSpec que o item 3 dá (o que o openspec update mudaria nos arquivos gerados); o plugin sdd (claude plugin list) na versão X.Y.0 do comum do kit, a única que o marketplace trilha-ai serve (num projeto noutra versão, a diferença vai à recomendação do kit.py atualizar); o gh e o Claude Code (gh --version, claude --version) diante da última versão publicada, como aviso. Se o OpenSpec da máquina estiver noutra versão que a do kit (a do modelo/.github/workflows/verificacao.yml), ou se o item 3 avisar que o openspec update mudaria arquivos gerados, recomende o python3 ferramentas/kit.py atualizar <pasta> --openspec, com o que ele pede e o que deixa por fazer. Ele instala a versão do kit na máquina toda (npm install -g), e não só para o projeto, quando a da máquina é outra. Se o aviso do item 3 lista arquivos em "apagaria", liste-os pelo openspec update --dry-run --json no projeto, que só lê (o aviso mostra só cinco), e diga que o comando os recusa e que a saída é escolha do usuário: deixá-los sair, acrescentando o --aceitar-apagados ao mesmo comando, ou, para um workflow fora do perfil, que é da máquina, pô-lo no perfil com openspec config profile, no terminal do usuário, respondendo não a "Apply changes to this project now?", sabendo que o próximo openspec update dos outros projetos também o cria neles. Se o CI do projeto fixa outra versão que a do kit, a troca é à mão no .github/workflows/verificacao.yml dele, e o --openspec não o muda; quando a do CI é a mais antiga, não recomende o npm install -g que o item 3 sugere, que levaria a máquina para trás: a correção é trocar a versão no CI.

Grave o relatório em <pasta>/docs/validacao-trilha-ai.md, sobrescrevendo o anterior, com:
- a data e a hora, lidas do `date`; a versão do comum no projeto e no kit;
- o veredito numa linha: "de acordo", "de acordo, com pendências" ou "não está de acordo";
- uma tabela com cada item de 1 a 9: o resultado (ok, aviso ou falha) e a evidência (o comando e a saída resumida);
- as pendências numeradas, cada uma com a correção recomendada.

No fim, responda em PT-BR, curto: o veredito, as pendências e o caminho do relatório. Pergunte se deve commitar o relatório; envio ao GitHub, só com "sim" explícito.
```
