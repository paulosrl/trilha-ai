O percurso inteiro de um projeto, da pasta vazia à change entregue, com o que acontece no seu computador e no GitHub em cada estação. Clique numa estação ou aperte Percorrer. Palavras como pull request, branch e merge são novas para você? Comece pela seção O que é um pull request.

O que é um pull request (PR)

PR é a sigla de pull request, que se traduz como "pedido de incorporação". É o jeito de propor uma mudança antes de ela entrar na versão oficial do projeto.

Pense num livro escrito a várias mãos. A versão oficial fica guardada, e ninguém escreve direto nela. Quem quer mudar um capítulo:

  1. Tira uma cópia e escreve nela.

    O livro oficial continua intacto enquanto a mudança é feita.

  2. Leva a cópia ao responsável.

    "Mudei isto, por este motivo; pode pôr no livro?" Esse pedido é o pull request.

  3. O responsável compara a cópia com o original, linha por linha.

    Vê o que mudou, comenta e pede ajustes, se for o caso.

  4. Aprovada, a mudança entra no livro oficial.

    Essa entrada é o merge.

No mapa, cada palavra tem o seu lugar no livro:

PalavraNo livroNo Trilha AI

mainO livro oficial.A branch principal, onde fica a versão que vale. A branch de cada change sai dela, atualizada, e volta a ela no merge.
commitUma página salva da cópia.Cada ponto salvo do trabalho, com uma mensagem que diz o que mudou. É também onde o trabalho recomeça se a sessão cair.
envioLevar a cópia para um cofre fora de casa.Mandar os commits ao GitHub (o git push), sempre com o seu "sim". Protege o trabalho da perda da máquina.
pull requestO pedido ao responsável.A página no GitHub que mostra tudo o que a change mudou. Nasce em rascunho no propose, para mostrar o plano antes do código, e sai do rascunho no archive.
verificaçãoUm revisor que confere sozinho.Os testes que o GitHub roda sozinho (o CI) em cada envio à main e em cada envio da branch depois que o pull request existe. Marcam o pull request com ✓ quando passam.
mergeA mudança entra no livro.A change entra na main, só com a verificação verde e o seu "sim". A change fecha aqui.

Por que o método usa o pull request: nenhuma change entra na versão oficial sem ser vista, revisada e testada antes; o trabalho fora de change e o fechamento do ANDAMENTO.md vão direto à main, e a verificação roda depois do envio. E, se algo der errado depois, o pull request fica como o registro do que mudou, quando e por quê.

Quem faz o commit?

O OpenSpec só lê e escreve arquivos: os da pasta openspec/ e, no openspec init e no openspec update, as skills e os comandos que ele gera para o Claude Code. A documentação oficial é direta: ele nunca faz commit, branch, push ou pull no seu projeto. No Trilha AI, quem decide quando fazer commit é o método, quem faz é o Claude e quem libera o envio é você.

Por que o archive fica dentro do pull request

O OpenSpec aceita arquivar a change antes ou depois do merge e pede só que o time escolha uma forma e a mantenha; a documentação dele recomenda arquivar depois do merge. O método arquiva antes, dentro do pull request da change.

  1. A main nunca fica em desacordo.

    Com o archive depois do merge, a main passaria um tempo com o código novo e os specs de antes dele.

  2. A change chega inteira, num só merge.

    O código, os specs, a tabela Ciclo e a página entram juntos. Arquivar depois pediria mais um envio à main só para o archive.

  3. A change fecha no merge.

    Depois do archive, a change some do openspec list; só o pull request diz se falta o merge. Por isso a retomada de uma sessão olha o PR, e o ANDAMENTO.md só volta a "nada em andamento" depois do merge.
